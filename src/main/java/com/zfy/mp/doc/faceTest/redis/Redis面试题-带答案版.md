## Redis 基础

### 1. Redis 是什么？它有什么特点？

Redis（Remote Dictionary Server）是一个基于 C 语言编写的开源内存数据库，使用 BSD 协议实现。

**特点**：
- **内存存储**：数据存储在内存中，读写性能极高
- **多种数据结构**：支持 String、Hash、List、Set、Zset 等 5 种基本类型 + 3 种特殊类型
- **持久化支持**：支持 RDB 和 AOF 两种持久化方式
- **高可用**：支持主从复制、哨兵、集群等模式
- **单线程**：采用单线程模型，避免锁竞争
- **协议简单**：基于 TCP 的请求/响应协议

---

### 2. Redis 和 Memcached 的区别是什么？各自适用于什么场景？

| 特性 | Redis | Memcached |
|------|-------|-----------|
| **数据类型** | 丰富（5种基本+3种特殊） | 仅字符串 |
| **持久化** | 支持 RDB 和 AOF | 不支持 |
| **集群** | 原生支持集群模式 | 需要二次开发 |
| **线程模型** | 单线程 + I/O 多路复用 | 多线程 |
| **存储方式** | 内存 + 持久化 | 仅内存 |
| **数据结构丰富度** | 高（可排序、可求交集等） | 低 |

**选择建议**：
- 需要复杂数据结构、持久化、集群 → Redis
- 仅做简单缓存、追求极致纯内存性能 → Memcached

## Redis 数据类型

### 3. Redis 有哪 5 种基本数据类型？各有什么特点？

| 类型 | 特点 | 底层实现 | 典型场景 |
|------|------|---------|---------|
| **String** | 二进制安全，可存储任何数据 | SDS | 缓存、计数器、分布式锁 |
| **List** | 双向链表，支持两端操作 | QuickList | 消息队列、最新列表 |
| **Hash** | 键值对映射，适合存储对象 | Dict/ZipList | 对象存储、购物车 |
| **Set** | 无序唯一，支持交并差 | Dict/Intset | 标签、好友关系、抽奖 |
| **Zset** | 有序唯一，通过 score 排序 | SkipList+Dict | 排行榜、优先级队列 |

---

### 4. String 类型的底层实现是什么？SDS 相比 C 字符串有什么优势？

**底层实现**：SDS（Simple Dynamic String，简单动态字符串）

**SDS 相比 C 字符串的优势**：

| 特性 | C 字符串 | SDS |
|------|---------|-----|
| **长度获取** | O(N)，需遍历 | O(1)，有 len 字段 |
| **缓冲区溢出** | 可能发生 | 不会，自动扩展 |
| **二进制安全** | 否，遇到 \0 截断 | 是，按长度处理 |
| **内存分配** | 固定 | 惰性释放 + 预分配 |

---

### 5. List 类型有哪些使用场景？如何用 List 实现队列和栈？

**使用场景**：
- 消息队列（不推荐，Redis Stream 更专业）
- 最新动态/文章列表
- 简单分页

**实现队列**（先进先出）：
```bash
RPUSH queue value    # 入队
LPOP queue           # 出队
```

**实现栈**（先进后出）：
```bash
RPUSH stack value    # 入栈
RPOP stack           # 出栈
```

---

### 6. Hash 类型适合存储什么数据？为什么？

**适合存储**：对象数据，如用户信息、商品信息、购物车内容。

**原因**：
- 相比 String（整个对象 JSON 序列化），可以单独修改字段
- 相比多个 String key，更节省内存（共享 key 前缀）
- 内存使用介于 ZipList 和 Dict 之间（小数据量用 ZipList）

---

### 7. Set 和 Zset 的区别是什么？Zset 的底层实现是什么？

**区别**：
- **Set**：无序集合，元素唯一，支持交并差操作
- **Zset**：有序集合，元素唯一但按 score 排序

**Zset 底层实现**：
- 小数据量（元素少、score 短）：ZipList
- 大数据量：SkipList（跳跃表） + Dict（字典）

SkipList 保证有序，Dict 保证 O(1) 查找。

---

### 8. 什么是 Bitmap？它有什么应用场景？

**概念**：Bitmap 是基于 String 类型的位操作，支持对每一位进行 SETBIT/GETBIT 操作。

**优势**：节省内存，适合大规模布尔统计。

**应用场景**：
- 用户每日签到统计
- 用户在线状态（365 天只占 46 字节/用户）
- 网站 UV 统计
- 统计连续登录天数

---

### 9. 什么是 HyperLogLog？它用于解决什么问题？

**概念**：HyperLogLog 是一种概率算法，用于估计集合中不重复元素的数量（基数统计）。

**特点**：
- 内存效率极高（每个 HyperLogLog 仅占 12KB）
- 允许一定误差（标准误差约 0.81%）
- 支持合并多个 HyperLogLog

**应用场景**：
- 独立访客（UV）统计
- 搜索词独立数量统计

---

### 10. GEO 类型是如何实现的？适合什么场景？

**实现**：GEO 基于 Zset 实现，底层使用 GeoHash 编码将经纬度转换为分数。

**常用命令**：
```bash
GEOADD city 116.4 39.2 "beijing"     # 添加位置
GEOPOS city "beijing"                # 获取位置
GEODIST city "beijing" "shanghai" km # 距离计算
GEORADIUS city 116.4 39.2 100 km    # 附近的人
```

**应用场景**：
- LBS 应用：附近的人、附近商家
- 滴滴打车：附近司机
- 美团/大众点评：附近餐厅

## Redis 持久化

### 11. Redis 有哪两种持久化方式？它们的原理是什么？

| 方式 | 原理 | 文件格式 |
|------|------|---------|
| **RDB** | 定时快照，将内存数据全量写入二进制文件 | 压缩的二进制文件 |
| **AOF** | 记录所有写操作命令到日志文件 | 文本文件（协议格式） |

---

### 12. RDB 持久化有什么优缺点？什么时候会触发？

**优点**：
- 恢复速度快（直接加载 .rdb 文件）
- 文件紧凑（全量备份）
- 适合备份和灾难恢复

**缺点**：
- 可能丢失最后一次快照后的数据
- 频繁快照会影响性能（fork 进程）

**触发方式**：
```bash
# 手动触发
SAVE                    # 同步阻塞
BGSAVE                  # 后台异步

# 自动触发（配置）
save m n   # m 秒内 n 次修改时触发
```

---

### 13. AOF 持久化有哪几种刷盘策略？默认是哪个？

| 策略 | 说明 | 安全性 | 性能 |
|------|------|--------|------|
| **always** | 每次写入都刷盘 | 最高 | 最低 |
| **everysec**（默认） | 每秒刷盘一次 | 较高 | 较高 |
| **no** | 由系统决定刷盘时机 | 可能丢数据 | 最高 |

---

### 14. AOF 重写是什么？为什么需要重写？

**概念**：AOF 重写（BGREWRITEAOF）压缩日志文件，去除无效命令（如被覆盖的 SET、多次 INCR）。

**原因**：
- AOF 文件会随时间不断增大
- 过大的 AOF 文件恢复慢、占用磁盘空间多
- 重写后文件更紧凑

**触发**：
```bash
BGREWRITEAOF   # 手动
auto-aof-rewrite-percentage 100  # 自动（文件比上次重写后增长 100%）
```

---

### 15. 同时开启 RDB 和 AOF 时，Redis 会优先使用哪个恢复数据？

**优先使用 AOF**。因为 AOF 记录更完整，通常丢失数据更少。

**原因**：
- AOF 刷盘频率更高（everysec 模式最多丢 1 秒数据）
- RDB 可能丢失上次快照后的所有数据

---

### 16. 如何选择合适的持久化策略？

| 场景 | 推荐策略 |
|------|---------|
| 仅做缓存 | 可以不用持久化 |
| 接受少量数据丢失 | RDB 即可 |
| 需要高数据安全性 | RDB + AOF 同时开启 |
| 追求最优性能 | AOF everysec + RDB 备份 |

**最佳实践**：同时开启 RDB 和 AOF，Redis 启动时优先加载 AOF。

## Redis 线程模型

### 17. Redis 是单线程的吗？为什么 Redis 这么快？

**回答**：Redis 4.0 之前核心网络模块是单线程，6.0 后部分多线程。核心命令执行始终单线程。

**快的原理**：
1. **内存操作**：数据在内存，I/O 不是瓶颈
2. **I/O 多路复用**：epoll/select/kqueue 高效管理多连接
3. **无锁竞争**：单线程无上下文切换和锁开销
4. **高效数据结构**：C 语言实现的 SDS、跳表等

---

### 18. Redis 6.0 引入的多线程是做什么的？核心执行还是单线程吗？

**多线程用途**：仅用于处理网络 I/O（协议解析和数据读写），核心命令执行仍是单线程。

**目的**：提升网络吞吐能力，充分利用多核 CPU。

**注意**：多线程仅是 I/O 层面的，命令执行、内存操作仍是单线程。

---

### 19. 什么是 I/O 多路复用？Redis 用的是什么？

**概念**：一个线程同时管理多个 socket 连接，收到 I/O 事件时通知应用处理。

**常见实现**：
- select
- poll
- **epoll**（Linux，Redis 使用）
- kqueue（Mac/BSD）

**Redis 选择 epoll 的原因**：高效，支持大量连接，O(1) 复杂度获取活跃连接。

## Redis 内存管理

### 20. Redis 有哪些内存淘汰策略？默认是哪个？

当内存达到 `maxmemory` 时，8 种淘汰策略：

| 策略 | 说明 |
|------|------|
| **noeviction**（默认） | 不淘汰，返回错误 |
| **volatile-lru** | LRU 淘汰设置了过期时间的键 |
| **allkeys-lru** | LRU 淘汰所有键 |
| **volatile-lfu** | LFU 淘汰设置了过期时间的键 |
| **allkeys-lfu** | LFU 淘汰所有键 |
| **volatile-random** | 随机淘汰设置了过期时间的键 |
| **allkeys-random** | 随机淘汰所有键 |
| **volatile-ttl** | 淘汰 TTL 最小的键 |

---

### 21. LRU、LFU、Random、TTL 算法的区别是什么？

| 算法 | 原理 | 适用场景 |
|------|------|---------|
| **LRU** | Least Recently Used，最近最少使用 | 热点数据保留 |
| **LFU** | Least Frequently Used，最不经常使用 | 长期热点数据 |
| **Random** | 随机淘汰 | 无规律访问 |
| **TTL** | 淘汰剩余时间最短的 | 临时数据清理 |

---

### 22. 什么是内存碎片？如何查看和清理？

**原因**：
- 键删除后内存未必立即归还系统
- 内存分配器（jemalloc）可能预留空间

**查看**：
```bash
INFO memory
# mem_fragmentation_ratio: 1.57
```

**处理**：
- 碎片率 < 1.5：正常，无需处理
- 碎片率 > 1.5：`MEMORY PURGE` 手动清理

---

### 23. 什么是 Bigkey？有什么危害？如何发现和处理？

**定义**：
- String 类型 value > 10MB
- Hash/Set/Zset 元素数量 > 100000

**危害**：
- 占用内存过大
- 网络传输慢（bigkey 查询阻塞）
- 操作耗时长（阻塞 Redis 主线程）

**发现**：
```bash
redis-cli --bigkeys              # 扫描大 key
redis-cli --scan | xargs ...     # 遍历分析
```

**处理**：
- 压缩大字符串（序列化）
- 拆分 Hash（field 分桶）
- 定期清理过期数据

---

### 24. Redis 的过期 key 删除策略是什么？

| 策略 | 说明 |
|------|------|
| **惰性删除** | 访问 key 时检查是否过期，过期则删除（CPU 友好，内存不友好） |
| **定期删除** | 定时任务随机抽查，设置过期时间的 key，删除过期的（折中方案） |
| **主动删除** | 内存不足时，触发淘汰策略删除 key |

**Redis 采用**：惰性删除 + 定期删除组合。

## Redis 事务

### 25. Redis 事务是如何实现的？有哪些命令？

**命令**：
```bash
MULTI        # 开启事务
EXEC         # 执行事务内所有命令
DISCARD      # 取消事务
```

**示例**：
```bash
MULTI
SET key1 value1
SET key2 value2
GET key1
EXEC
```

---

### 26. WATCH 命令的作用是什么？如何实现乐观锁？

**作用**：监控一个或多个 key，如果在事务执行前被其他命令修改，事务将自动取消（返回空）。

**实现乐观锁**：
```bash
WATCH balance
balance=$(GET balance)
if [ $balance -ge 100 ]; then
    MULTI
    DECRBY balance 100
    EXEC
else
    echo "余额不足"
fi
```

**原理**：WATCH 记录 key 的版本号，EXEC 时检查是否变化。

---

### 27. Redis 事务为什么不支持回滚？和传统数据库事务有什么区别？

**不支持回滚的原因**：
- Redis 设计理念是简单高性能
- 命令错误是编程错误，应提前避免
- 大部分错误是语法错误，可在开发阶段发现

**与传统数据库对比**：

| 特性 | Redis 事务 | 数据库事务 |
|------|-----------|-----------|
| **原子性** | 命令批量执行，不保证部分成功 | 全部成功或全部回滚 |
| **一致性** | 不保证（错误命令不执行） | 保证 |
| **隔离性** | WATCH 实现乐观锁 | MVCC/锁 |
| **持久性** | 不保证（内存操作） | 保证（redo log） |

---

### 28. DISCARD 命令的作用是什么？

**作用**：在事务执行前（EXEC 之前），取消当前事务，丢弃所有命令。

```bash
MULTI
SET key1 value1
DISCARD      # 取消事务，key1 不会被设置
```

## Redis 性能优化

### 29. 如何定位 Redis 的慢查询？

**步骤**：
```bash
# 1. 开启慢查询日志
CONFIG SET slowlog-log-slower-than 1000   # 超过 1ms 记录

# 2. 查看慢查询
SLOWLOG GET 10        # 最近 10 条

# 3. 分析
SLOWLOG LEN           # 总数量
```

**优化思路**：
- 减少慢命令使用（避免 O(N) 命令）
- 合理使用 Pipeline
- 避免 bigkey

---

### 30. Bigkey 会造成什么问题？如何优化？

**问题**：
- 占用内存大
- 查询/删除操作阻塞主线程
- 网络传输慢
- 导致主从同步延迟

**优化方案**：
- 压缩字符串（序列化存储）
- 拆分 Hash（按 field 数量或业务分桶）
- 异步删除（UNLINK 代替 DEL）
- 使用合理的数据结构

---

### 31. Pipeline 有什么用？它和批量命令有什么区别？

**Pipeline**：将多个命令打包一次发送，减少网络 RTT（Round Trip Time）。

**批量命令 vs Pipeline**：

| 特性 | 批量命令（MGET/MSET） | Pipeline |
|------|---------------------|---------|
| 命令数量 | 有限（同一类型） | 无限制 |
| 网络次数 | 1 次 | 1 次 |
| 原子性 | 支持 | 不支持（无事务） |

**示例**：
```bash
# 普通方式：N 次 RTT
GET key1
GET key2
GET key3

# Pipeline：1 次 RTT
(echo -e "GET key1\r\nGET key2\r\nGET key3\r\n"; sleep 1) | nc localhost 6379
```

---

### 32. 如何提高缓存命中率？

| 方法 | 说明 |
|------|------|
| 合理设置 TTL | 既不过长（数据陈旧）也不过短（频繁穿透） |
| 避免冷数据占用缓存 | 使用 LRU/LFU 淘汰策略 |
| 使用合适的数据结构 | 选择最优的数据类型 |
| 预热热点数据 | 启动时加载热点 key |
| 避免大 key | 分散热点，避免 bigkey 淘汰一片 |

---

### 33. Redis 客户端连接数过多会有什么影响？如何优化？

**影响**：
- 消耗内存
- 每个连接占用文件描述符
- 过多命令排队阻塞

**优化方案**：
- 使用连接池复用连接
- 配置 `maxclients` 限制
- 客户端批量操作减少连接创建
- 部署多个 Redis 实例分散连接

## Redis 缓存问题

### 34. 什么是缓存穿透？有哪些解决方案？

**问题**：查询不存在的数据，每次都打到数据库。

**解决方案**：
1. **缓存空值**：将空结果缓存短时间（TTL 短）
2. **布隆过滤器**：判断 key 是否存在，存在才查 DB
3. **参数校验**：拦截非法请求（如 id < 0）

---

### 35. 什么是缓存击穿？有哪些解决方案？

**问题**：热点 key 过期瞬间，大量请求击穿到数据库（类似 DB 慢查询）。

**解决方案**：
1. **互斥锁**：只允许一个线程重建缓存（SETNX）
2. **热点数据永不过期**：物理不过期，定期异步更新
3. **限流降级**：保护数据库

---

### 36. 什么是缓存雪崩？有哪些解决方案？

**问题**：大量 key 同时过期或 Redis 宕机，导致数据库压力骤增。

**解决方案**：
1. **过期时间随机化**：`TTL + random()` 避免同时过期
2. **高可用架构**：主从 + 哨兵 / Cluster
3. **限流降级**：保护数据库
4. **提前演练**：做好应急预案

---

### 37. 缓存穿透、击穿、雪崩三者有什么区别？

| 问题 | 原因 | 结果 | 侧重点 |
|------|------|------|--------|
| **穿透** | 查询不存在的数据 | 每次都打爆 DB | 数据本来就不存在 |
| **击穿** | 热点 key 过期瞬间 | 瞬间大量请求打爆 DB | 单个热点 key |
| **雪崩** | 大量 key 同时过期 / Redis 宕机 | 数据库压力骤增 | 大面积 key |

---

### 38. 如何保证 Redis 和数据库的双写一致性？

**Cache Aside（最常用）**：
- 读：先读缓存，缓存没有则读 DB 并更新缓存
- 写：先更新 DB，再删除缓存

**注意问题**：
- 并发下可能短暂不一致
- 删除缓存失败会导致不一致
- 可用延迟双删或消息队列补偿

---

### 39. 什么是延迟双删？为什么要用它？

**延迟双删**：先删除缓存 → 更新 DB → 延迟一段时间再删除缓存。

**为什么用**：
- 解决并发下，线程 A 读缓存（未命中）→ 查 DB → 线程 B 更新 DB → 线程 B 删除缓存 → 线程 A 写缓存（脏数据）
- 延迟确保线程 A 完成写入后再删

---

### 40. Cache Aside 模式的工作流程是什么？

**读操作**：
```
1. 请求读 key
2. Redis 有 → 返回
3. Redis 无 → 查数据库 → 写入 Redis → 返回
```

**写操作**：
```
1. 更新数据库
2. 删除缓存（不是更新缓存）
```

**为什么删除而不是更新**：并发下更新可能导致脏读。

## Redis 集群

### 41. 主从复制的工作原理是什么？有哪些同步方式？

**同步方式**：
- **SYNC**：全量同步（第一次连接或断线重连）
- **PSYNC2**：部分同步（断线重连后增量同步）

**工作原理**：
1. 从节点发送 `PSYNC` 给主节点
2. 主节点 fork 进程生成 RDB 文件
3. 发送 RDB 给从节点
4. 从节点加载 RDB 完成全量同步
5. 后续增量同步通过命令传播

---

### 42. 主从复制有哪些问题？为什么需要哨兵？

**问题**：
- 主节点宕机需要手动切换
- 无法自动故障转移
- 手动干预期间服务不可用

**为什么需要哨兵**：自动监控、主从切换，保证高可用。

---

### 43. 哨兵模式有什么作用？它是如何监控和故障转移的？

**作用**：
1. 监控主从节点健康状态
2. 自动故障转移（主节点宕机时提升从节点）
3. 通知应用新的主节点地址

**故障转移流程**：
1. 哨兵每秒 ping 主节点
2. 主节点无响应超过阈值 → 标记为主观下线
3. 多个哨兵投票，超过 quorum → 标记为客观下线
4. 投票选出一个从节点作为新主节点
5. 通知所有从节点切换
6. 告知应用新的主节点地址

---

### 44. Redis Cluster 是如何实现数据分片的？

**原理**：
- 共有 16384 个槽位（slot）
- 每个主节点负责一部分槽位
- 客户端可连接任意节点，节点间自动转发

**槽位分配**：
- 官方建议：每个主节点平均分配 5460 个槽位
- 可手动分配：`redis-cli --cluster rebalance`

---

### 45. Redis Cluster 的槽位是如何计算的？

```
slot = CRC16(key) % 16384
```

**CRC16**：对 key 进行 CRC16 校验和计算。

**示例**：
```bash
SET key1 value1   # key1 可能被分配到 slot 12182
SET key2 value2   # key2 可能被分配到 slot 1536
```

### 46. 主从、哨兵、Cluster 三种模式有什么区别？

| 模式 | 复制方式 | 故障自动切换 | 数据分片 | 客户端连接 |
|------|---------|-------------|---------|-----------|
| **主从** | 异步 | 否 | 否 | 任意节点 |
| **哨兵** | 异步 | 是 | 否 | 任意节点 |
| **Cluster** | 异步 | 是 | 是 | 任意节点 |

### 47. 如何实现 Redis 分布式锁？需要注意什么？

**基本实现**：
```bash
SET lock_key unique_value NX PX 30000
```

**注意**：
- **value 要唯一**：释放锁时验证 value，防止误删
- **设置过期时间**：防止死锁
- **原子性**：必须用 SETNX

**释放锁（Lua 脚本）**：
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 48. RedLock 算法是什么？为什么要用它？

**概念**：RedLock 通过多数节点投票实现更可靠的分布式锁。

**原理**：
1. 依次向 N 个 Redis 实例获取锁
2. 超过半数实例成功获取锁才算成功
3. 失败时向所有实例释放锁

**为什么用**：单节点 Redis 锁在主从切换时可能丢失，RedLock 通过多节点保证。

---

### 49. Redis Cluster 支持跨槽操作吗？

**不支持跨槽 MGET/MSET 等批量操作**。

**解决方案**：
- 客户端计算 key 所属槽位，相同槽位才批量
- 或使用 Hash Tag 强制 key 路由到同一槽位

**Hash Tag**：
```
# 使用 {} 包裹相同部分，会被用于计算槽位
{user:1}:name
{user:1}:age
```

### 50. 哨兵模式下的客户端如何感知主从切换？

**方式**：
1. 哨兵通知：订阅哨兵的 +switch-master 频道
2. 客户端注册：启动时连接哨兵，获取主节点地址
3. 哨兵主动推送：主从切换后推送新地址

### 52. 如何设计一个 Redis 缓存架构？

**分层缓存**：
```
用户请求 → CDN（静态资源）→ Nginx（网关）→ 应用服务 → Redis（分布式缓存）→ MySQL
```

**常见模式**：
1. **Cache Aside**：应用自行管理缓存（最常用）
2. **Read Through**：缓存自动加载
3. **Write Through**：写缓存同时写 DB
4. **Write Behind**：异步写 DB

**注意事项**：
- 容量规划（根据数据量计算内存）
- Key 命名规范
- 过期策略设计
- 监控报警
- 应急预案

### 53. Redis 挂了怎么办？有哪些应急预案？

**预案**：
1. **Redis 宕机**：
   - 切换到数据库降级模式
   - 限流保护数据库
   - 快速重启或切换从节点

2. **主从都宕机**：
   - 停止部分写服务
   - 从本地缓存临时服务
   - 紧急启动新 Redis

3. **预防措施**：
   - 开启持久化（RDB + AOF）
   - 配置哨兵/集群高可用
   - 定期备份数据
   - 监控告警
   - 定期演练
