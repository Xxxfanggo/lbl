## MySQL 基础

### 1. 什么是关系型数据库？和非关系型数据库有什么区别？

**关系型数据库（RDB）**：基于关系模型（二维表结构）的数据库，数据存放在表中，表与表之间可以建立关系。主流产品：MySQL、PostgreSQL、Oracle、SQL Server。

**非关系型数据库（NoSQL）**：泛指非关系型数据库，常见类型：
- **键值型**：Redis、Memcached
- **文档型**：MongoDB
- **列族型**：HBase、Cassandra
- **图形型**：Neo4j

**主要区别**：

| 维度 | 关系型数据库 | 非关系型数据库 |
|------|-------------|---------------|
| **数据结构** | 二维表结构 | 多样化（K-V、文档、列族等） |
| **事务支持** | ACID 强事务 | 弱事务或无事务 |
| **扩展方式** | 垂直扩展（Scale Up） | 水平扩展（Scale Out） |
| **查询能力** | SQL 语句，关联查询强 | 查询能力有限 |
| **典型场景** | 业务系统、财务系统 | 缓存、日志、实时分析 |

---

### 2. 什么是 SQL？SQL 有哪些分类？

**SQL（Structured Query Language）**：结构化查询语言，是与数据库交互的标准语言。

**SQL 分类**：

| 分类 | 说明 | 典型语句 |
|------|------|----------|
| **DDL**（数据定义语言） | 定义数据库对象（库、表、索引等） | CREATE、DROP、ALTER |
| **DML**（数据操作语言） | 操作数据 | SELECT、INSERT、UPDATE、DELETE |
| **DCL**（数据控制语言） | 控制权限 | GRANT、REVOKE |
| **TCL**（事务控制语言） | 管理事务 | COMMIT、ROLLBACK、SAVEPOINT |

---

### 3. 什么是 MySQL？它有什么特点？

**MySQL**：一款开源的关系型数据库管理系统，最初由瑞典 MySQL AB 公司开发，现属于 Oracle 旗下产品。默认端口 **3306**。

**主要特点**：
- 开源免费，社区活跃
- 支持 ACID 事务（InnoDB 引擎）
- 支持多种存储引擎
- 主从复制、读写分离
- 性能优异，可扩展性强

---

### 4. MySQL 为什么如此流行？相比其他数据库有什么优势？

**MySQL 的优势**：

1. **成本**：开源免费，社区版功能足够丰富
2. **性能**：高并发读写性能优秀
3. **生态**：文档丰富、社区活跃、周边工具完善
4. **易用**：安装配置简单，学习曲线平缓
5. **可靠**：成熟稳定，崩溃恢复机制完善
6. **兼容**：支持标准 SQL，主从复制成熟

**与 Oracle/SQL Server 对比**：免费、轻量级
**与 PostgreSQL 对比**：更成熟的主从复制生态
**与 MongoDB 对比**：强事务支持，关联查询能力

## MySQL 字段类型

### 5. CHAR 和 VARCHAR 的区别是什么？分别在什么场景下使用？

| 区别 | CHAR | VARCHAR |
|------|------|---------|
| **存储方式** | 定长，不足部分填充空格 | 变长，需要 1-2 字节记录长度 |
| **最大长度** | 255 字符 | 65535 字节 |
| **检索效率** | 更高（无需计算长度） | 略低 |
| **存储空间** | 固定长度 | 可变 |

**使用场景**：
- **CHAR**：长度固定或接近固定（如密码 MD5 值、身份证号、性别）
- **VARCHAR**：长度差异大或不确定（如昵称、地址、文章标题）

---

### 6. VARCHAR(100) 和 VARCHAR(10) 的区别？存储空间一样吗？

**存储空间**：存储相同内容时，占用磁盘空间相同。

**主要区别**：

| 区别 | VARCHAR(100) | VARCHAR(10) |
|------|--------------|-------------|
| **内存占用** | 排序/创建临时表时分配 100 字符内存 | 只分配 10 字符 |
| **业务扩展性** | 更好，无需修改表结构 | 受限，可能需要 ALTER |
| **索引效率** | 可能更低（InnoDB 最大 767 字节） | 更高 |

**建议**：定义足够大但不过分的的长度，平衡扩展性和性能。

---

### 7. DECIMAL 和 FLOAT/DOUBLE 的区别？为什么金额要用 DECIMAL 存储？

| 类型 | 存储方式 | 精度 | 典型场景 |
|------|----------|------|----------|
| **DECIMAL** | 定点数，字符串存储 | 精确 | 货币金额 |
| **FLOAT** | 浮点数 | 近似（7 位有效数字） | 科学计算 |
| **DOUBLE** | 双精度浮点 | 近似（15 位有效数字） | 科学计算 |

**金额用 DECIMAL 的原因**：
- FLOAT/DOUBLE 会产生精度丢失（如 0.1 + 0.2 ≠ 0.3）
- DECIMAL 是精确小数，不会出现舍入误差
- 金融场景对精度要求极高

**建议**：`DECIMAL(10, 2)` 表示总共 10 位，小数点后 2 位。

---

### 8. DATETIME 和 TIMESTAMP 的区别？如何选择？

| 区别 | DATETIME | TIMESTAMP |
|------|----------|-----------|
| **时区** | 无，存储原始值 | 有，自动转 UTC 和本地时区 |
| **存储空间** | 5-8 字节 | 4-7 字节 |
| **时间范围** | 1000-01-01 ~ 9999-12-31 | 1970-01-01 ~ 2038-01-19 |
| **默认值** | 无 | CURRENT_TIMESTAMP |
| **更新触发** | 不会 | 行修改时自动更新 |

**选择建议**：
- 需要多时区支持 → **TIMESTAMP**
- 需要表示 2038 年后时间 → **DATETIME**
- 追求性能和数据量 → **整数型时间戳**

---

### 9. 为什么不要推荐使用 TEXT 和 BLOB？有什么替代方案？

**TEXT/BLOB 的问题**：

1. 不能有默认值
2. 临时表无法使用内存临时表
3. 检索效率低（不支持全文索引前的版本）
4. 不能直接创建索引（需前缀索引）
5. 消耗大量网络和 IO 带宽
6. 并发连接数受限

**替代方案**：

| 场景 | 替代方案 |
|------|----------|
| 短文本 | VARCHAR |
| 长文本（日志、评论） | 业务层压缩或拆分 |
| 富文本内容 | 存 HTML，单独字段存纯文本 |
| 图片/文件 | 存 OSS URL，文件存对象存储 |
| JSON 数据 | JSON 类型（MySQL 5.7+） |

---

### 10. NULL 和空字符串 '' 的区别是什么？

| 区别 | NULL | 空字符串 '' |
|------|------|-------------|
| **占用空间** | 实际不存储 | 存储一个空字符 |
| **查询语法** | `IS NULL` / `IS NOT NULL` | `= ''` / `!= ''` |
| **COUNT 计数** | 不计数 | 计数 |
| **索引** | 可建，但影响索引效率 | 正常索引 |
| **聚合函数** | 通常忽略 | 参与计算 |
| **语义** | 未知/不存在 | 已知为空 |

**建议**：尽量避免 NULL，可用 0、''、-1 等默认值替代。

---

### 11. 手机号存储用 INT 还是 VARCHAR？为什么？

**答案：用 VARCHAR**

**原因**：

1. **位数问题**：手机号可能以 0 开头（如 086、+86），INT 会丢失前导 0
2. **长度问题**：手机号超过 10 位，INT 范围有限
3. **语义问题**：手机号不是数字，是字符串
4. **查询问题**：手机号通常用于精确匹配或 LIKE 模糊查询，不是用于计算

**存储建议**：`VARCHAR(20)`，留有余量支持国际号码格式。

## MySQL 基础架构

### 12. 请描述一下 MySQL 的执行流程？

```
连接器 → 查询缓存 → 分析器 → 优化器 → 执行器 → 存储引擎
```

**详细流程**：

1. **连接器**：身份认证（用户名密码）、权限验证、连接管理
2. **查询缓存**（MySQL 8.0 已移除）：检查是否命中缓存
3. **分析器**：词法分析（识别关键字）、语法分析（检查语法）
4. **优化器**：选择最优执行计划（索引选择、JOIN 顺序）
5. **执行器**：调用存储引擎接口执行，权限再校验
6. **存储引擎**：具体读写数据（InnoDB/MyISAM 等）

---

### 13. MySQL 有哪些核心组件？各自的作用是什么？

| 组件 | 作用 |
|------|------|
| **连接器** | 管理连接、身份认证、权限验证 |
| **查询缓存**（已移除） | 缓存 SELECT 结果 |
| **分析器** | 词法分析、语法分析 |
| **优化器** | 生成执行计划、选择索引 |
| **执行器** | 调用存储引擎执行操作 |
| **存储引擎** | 实际读写数据（插件式架构） |

---

### 14. Server 层和存储引擎层分别负责什么？

**Server 层**（MySQL 前端）：
- 连接管理、查询缓存
- SQL 解析、优化、执行
- 内置函数（日期、数学、字符串等）
- **binlog 日志**
- 跨引擎功能（如触发器、视图）

**存储引擎层**（MySQL 后端）：
- 数据存储和读取
- 索引管理
- 事务支持（InnoDB）
- 崩溃恢复（InnoDB）
- **redo log、undo log**（InnoDB）

## MySQL 存储引擎

### 15. MySQL 支持哪些存储引擎？默认使用的是哪个？

**常见存储引擎**：

| 引擎 | 特点 | 使用场景 |
|------|------|----------|
| **InnoDB** | 默认，支持事务、行锁、MVCC | OLTP、业务系统 |
| **MyISAM** | 不支持事务、表锁 | 读多写少、日志 |
| **Memory** | 数据存内存，速度快 | 临时表、缓存 |
| **Archive** | 压缩，只支持 INSERT/SELECT | 归档、日志 |
| **CSV** | CSV 格式存储 | 数据导入导出 |

---

### 16. MyISAM 和 InnoDB 的区别是什么？

| 特性 | MyISAM | InnoDB |
|------|--------|--------|
| **锁粒度** | 表级锁 | 行级锁（默认） |
| **事务支持** | ❌ 不支持 | ✅ 支持 |
| **外键支持** | ❌ 不支持 | ✅ 支持 |
| **崩溃恢复** | ❌ 不支持 | ✅ 支持（redo log） |
| **MVCC** | ❌ 不支持 | ✅ 支持 |
| **索引结构** | 非聚簇索引 | 聚簇索引 |
| **全文索引** | ✅ 支持 | ✅ 支持（5.6+） |
| **性能特点** | 读多写少性能好 | 高并发读写更好 |
| **Count(*)** | 存具体值，快 | 需扫描，慢 |

---

### 17. InnoDB 为什么成为默认引擎？它有哪些核心特性？

**成为默认引擎的原因**：

1. **事务支持**：完整 ACID 事务支持
2. **行级锁**：高并发下性能优秀
3. **崩溃恢复**：通过 redo log 实现崩溃恢复
4. **MVCC**：读写并发不阻塞
5. **外键支持**：保证参照完整性
6. **聚簇索引**：查询性能优异

**核心特性**：事务、行锁、MVCC、崩溃恢复、聚簇索引、外键

---

### 18. InnoDB 和 MyISAM 的索引实现有什么区别？

| 区别 | InnoDB | MyISAM |
|------|--------|--------|
| **索引类型** | 聚簇索引（数据在叶子节点） | 非聚簇索引（索引和数据分离） |
| **主键索引** | 主键索引即数据 | 主键索引指向数据地址 |
| **辅助索引** | 叶子节点存主键值，需回表 | 叶子节点存数据地址 |
| **索引缓存** | 缓存索引和数据 | 只缓存索引 |

**InnoDB 聚簇索引优点**：查询直接获取数据，无需回表。
**InnoDB 聚簇索引缺点**：主键过大时，辅助索引体积大。

---

### 19. 一张表只能有一个主键吗？主键应该如何选择？

**主键规则**：
- 一张表**只能有一个**主键
- 主键必须唯一且非空
- 主键可以由多个列组成（复合主键）

**主键选择建议**：

| 类型 | 优点 | 缺点 |
|------|------|------|
| **自增整型** | 写入性能好，占用空间小 | 分布式环境下可能不连续 |
| **UUID** | 全球唯一 | 占用空间大，UUID 无序，页分裂 |
| **雪花算法** | 有序，性能好 | 依赖机器时间 |

**最佳实践**：
- 优先使用 **自增 BIGINT** 作为主键
- 避免使用 UUID 或字符串作为主键
- 无主键时，InnoDB 会生成隐藏主键

## MySQL 索引

### 20. 什么是索引？索引的本质是什么？

**索引**：一种用于快速查询和检索数据的数据结构，本质是**排好序的数据结构**。

**本质**：索引 = 数据结构 + 有序排列

**目的**：减少磁盘 IO次数，加快查询速度。

---

### 21. 索引为什么能提高查询效率？

**核心原因**：减少磁盘 IO

| 效率对比 | 无索引 | 有索引 |
|----------|--------|--------|
| **查找方式** | 全表扫描 | 索引树定位 |
| **IO 次数** | 全量数据页 | 索引树高度（3-4 次） |
| **时间复杂度** | O(n) | O(log n) |

**B+树索引特点**：
- 矮胖型，树高通常 3-4 层
- 叶子节点用链表连接，范围查询友好
- 非叶子节点不存储数据，可容纳更多索引键

---

### 22. MySQL 为什么选择 B+树而不是 B 树作为索引结构？

**B 树的问题**：
- 非叶子节点也存储数据
- 导致每个节点可存储的索引键减少
- 树高增加，IO 次数增多

**B+树的优势**：
- 非叶子节点不存储数据，只存储索引键
- 每个节点可容纳更多索引键
- 树高更低，IO 次数更少
- 所有数据在叶子节点，查询时间更稳定
- 叶子节点双向链表，范围查询极快

---

### 23. B+树相比 B 树有哪些优势？

1. **I/O 效率更高**：非叶子节点不存数据，单次 IO 能加载更多索引
2. **查询性能稳定**：必须到叶子节点才能找到数据
3. **范围查询友好**：叶子节点双向链表支持快速范围查询
4. **更适合排序**：叶子节点有序，便于 ORDER BY
5. **空间利用率高**：非叶子节点只存索引，存储密度更大

---

### 24. 什么是聚簇索引和非聚簇索引？有什么区别？

| 类型 | 别名 | 特点 |
|------|------|------|
| **聚簇索引** | 聚集索引、簇索引 | 叶子节点存储完整数据，一个表只能有一个 |
| **非聚簇索引** | 二级索引、辅助索引 | 叶子节点存储主键值，需要回表 |

**InnoDB 聚簇索引**：
- 主键索引 = 聚簇索引
- 叶子节点存储完整行数据
- 辅助索引叶子节点存主键值

**MyISAM 非聚簇索引**：
- 索引树叶子节点存储数据地址
- 数据和索引分离

---

### 25. 什么是覆盖索引？如何实现？

**覆盖索引**：查询的字段正好是索引的字段，无需回表。

**示例**：
```sql
-- 表：tb_user (id, name, age, email)
-- 索引：idx_name_age (name, age)

-- 命中覆盖索引，无需回表
SELECT name, age FROM tb_user WHERE name = '张三';

-- 未命中覆盖索引，需要回表
SELECT * FROM tb_user WHERE name = '张三';
```

**实现方式**：
- 将需要查询的字段纳入索引
- 遵循最左前缀原则
- 优先选择覆盖索引作为优化手段

---

### 26. 什么是联合索引？什么是最左前缀原则？

**联合索引**：多列组合成一个索引，如 `idx_a_b_c (a, b, c)`。

**最左前缀原则**：查询条件从索引最左边开始连续匹配，才能使用索引。

**联合索引 (a, b, c) 的匹配规则**：

| 查询条件 | 是否走索引 | 原因 |
|----------|-----------|------|
| `a = 1` | ✅ | 命中最左前缀 |
| `a = 1 AND b = 1` | ✅ | 连续命中 |
| `a = 1 AND b = 1 AND c = 1` | ✅ | 完全命中 |
| `b = 1` | ❌ | 违背最左前缀 |
| `c = 1` | ❌ | 违背最左前缀 |
| `a = 1 AND c = 1` | ✅ | a 生效，c 不生效（中断） |

---

### 27. 联合索引 (a,b,c)，查询 a=1 AND c=1 会走索引吗？b=1 AND c=1 呢？

**a=1 AND c=1**：
- **走索引，但只用到 a 列**
- a 能命中，但 c 不连续，无法直接用 b 跳到 c

**b=1 AND c=1**：
- **不走索引**
- 完全违背最左前缀原则

**优化建议**：如需优化 c 列查询，可使用 `idx_a_c (a, c)` 覆盖此查询。

---

### 28. 哪些场景会导致索引失效？

1. **违背最左前缀原则**
2. **索引列上进行计算、函数、类型转换**
   ```sql
   -- 失效
   SELECT * FROM tb WHERE YEAR(date) = 2024
   -- 正确
   SELECT * FROM tb WHERE date >= '2024-01-01' AND date < '2025-01-01'
   ```
3. **以 % 开头的 LIKE 查询**
   ```sql
   -- 失效
   SELECT * FROM tb WHERE name LIKE '%张'
   -- 有效
   SELECT * FROM tb WHERE name LIKE '张%'
   ```
4. **OR 连接的条件中有一个没有索引**
5. **IN 取值范围过大**（MySQL 优化器认为全表扫描更快）
6. **隐式类型转换**
   ```sql
   -- phone 是 VARCHAR，数字会隐式转换，索引失效
   SELECT * FROM tb WHERE phone = 13800138000
   ```

### 29. 什么是索引下推（ICP）？它是如何优化的？

**索引下推（Index Condition Pushdown，ICP）**：MySQL 5.6 引入的优化，在索引遍历时**在存储引擎层**就执行 WHERE 条件，过滤掉不符合条件的记录，减少回表次数。

**ICP 优化示例**：
```sql
-- 表：tb_user (id, name, age, email)
-- 索引：idx_name_age (name, age)

SELECT * FROM tb_user WHERE name LIKE '张%' AND age = 19;
```

**优化前（MySQL 5.5）**：
- 先根据 `name LIKE '张%'` 找到所有匹配的索引
- 回表获取完整记录
- 再在 Server 层过滤 `age = 19`

**优化后（MySQL 5.6+）**：
- 在索引遍历时同时过滤 `name LIKE '张%' AND age = 19`
- 只回表获取符合所有条件的记录
- **减少回表次数**

---

### 30. 如何设计合理的索引？有哪些原则？

1. **区分度高的列优先**：区分度越高，索引效果越好（如主键、唯一键）
2. **尽量使用覆盖索引**：避免回表
3. **遵循最左前缀原则**：合理安排列顺序
4. **控制索引数量**：单表索引不超过 5 个（写操作负担）
5. **避免冗余索引**：如已有 (a, b)，则 (a) 是冗余的
6. **考虑查询类型**：等值查询用 B-Tree，范围查询可考虑索引顺序
7. **前缀索引**：长字符串列可用前缀索引

---

### 31. SELECT * 会导致索引失效吗？为什么？

**结论**：不一定会失效，但**不推荐使用**。

**分析**：
- `SELECT *` 本身不影响索引是否被使用
- 索引是否能被使用，取决于 WHERE 条件

**但 SELECT * 会**：
1. 无法使用覆盖索引优化，增加回表
2. 增加网络带宽消耗
3. 表结构变更时可能出错
4. 增加 CPU 消耗（解析不需要的字段）

**最佳实践**：只查询需要的字段。

---

### 32. 什么是索引跳跃扫描（Index Skip Scan）？

**索引跳跃扫描**：MySQL 8.0 引入的优化，当索引第一列区分度不高，但第二列区分度高时，优化器可以跳过第一列直接使用第二列。

**示例**：
```sql
-- 表：tb_order (gender, age, email)
-- 索引：idx_gender_age (gender, age)

SELECT age FROM tb_order WHERE age = 20;
```

**传统执行**：无法使用 idx_gender_age（违背最左前缀）

**索引跳跃扫描**：MySQL 8.0+ 优化器可能跳过 gender 列，直接使用 age 索引。

**注意**：这是优化手段，不是索引设计原则，尽量避免依赖此特性。

## MySQL 查询缓存

### 33. 什么是查询缓存？MySQL 8.0 为什么移除了它？

**查询缓存**：缓存 SELECT 语句及其结果，当相同查询再次执行时，直接返回缓存结果。

**移除原因**（MySQL 8.0）：
1. **命中率低**：任何细微差异（空格、大小写、注释）都不命中
2. **维护成本高**：表数据变更时，相关缓存全部失效
3. **并发性能差**：使用互斥锁，高并发下成为瓶颈
4. **内存碎片**：缓存存储结构导致内存碎片化

---

### 34. 查询缓存的优缺点是什么？

**优点**：
- 相同查询直接返回缓存，性能极高

**缺点**：
1. **全局互斥锁**：高并发下性能急剧下降
2. **缓存失效频繁**：任何表数据变更导致相关缓存全部失效
3. **内存碎片**：Query Cache 40% 碎片率常见
4. **命中率低**：查询细微差异导致不命中
5. **资源消耗**：占用内存，影响其他功能

**替代方案**：应用层缓存（Redis、Memcached）。

## MySQL 日志

### 35. MySQL 有哪三大日志？它们的作用分别是什么？

| 日志 | 类型 | 作用 | 所属模块 |
|------|------|------|----------|
| **redo log** | 物理日志 | 崩溃恢复、事务持久性 | InnoDB |
| **binlog** | 逻辑日志 | 数据归档、主从复制 | Server 层 |
| **undo log** | 逻辑日志 | 回滚事务、MVCC | InnoDB |

**其他日志**：error log、slow log、relay log、general log

---

### 36. redo log 是什么？为什么需要 redo log？

**redo log（重做日志）**：InnoDB 特有的日志，记录数据页的物理变化。

**为什么需要 redo log**：

1. **保证事务持久性**：事务提交后，即使系统崩溃也能恢复
2. **随机写优化**：先写 redo log（顺序写），再批量刷新数据页（随机写）
3. **崩溃恢复**：系统异常重启时，恢复未刷新到磁盘的数据

**redo log 的特点**：
- 物理日志，记录数据页变化
- 循环写，空间固定
- 崩溃恢复的唯一依据

---

### 37. redo log 的刷盘策略有哪些？默认是哪个？

**参数**：`innodb_flush_log_at_trx_commit`

| 值 | 行为 | 安全性 | 性能 |
|----|------|--------|------|
| **0** | 事务提交不刷盘，每秒从 page cache 刷盘 | 可能丢失 1 秒数据 | 最快 |
| **1**（默认） | 事务提交立刻刷盘 | 不会丢失数据 | 最慢 |
| **2** | 只写到 page cache，不刷盘 | MySQL 挂不丢，OS 挂丢 | 较快 |

**建议**：生产环境必须设为 1，保证数据不丢失。

---

### 38. binlog 是什么？它和 redo log 有什么区别？

**binlog（归档日志）**：Server 层日志，记录数据变更的逻辑操作。

**binlog vs redo log**：

| 区别 | binlog | redo log |
|------|--------|----------|
| **所属模块** | Server 层 | InnoDB 存储引擎 |
| **日志类型** | 逻辑日志（SQL 语句） | 物理日志（数据页变化） |
| **记录内容** | 数据的修改逻辑 | 物理修改内容 |
| **写入方式** | 追加写 | 循环写 |
| **用途** | 主从复制、数据归档 | 崩溃恢复 |
| **是否必须** | 可选（可关闭） | InnoDB 必须 |

---

### 39. binlog 有哪三种格式？有什么区别？生产环境应该用哪个？

| 格式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **STATEMENT** | 记录修改数据的 SQL | 日志量小 | 函数、存储过程可能不一致 |
| **ROW** | 记录每行数据的变化 | 数据一致性强 | 日志量大（可达 10 倍） |
| **MIXED** | 混合使用 statement 和 row | 平衡 | 可能出现混合格式 |

**生产环境建议**：**ROW 格式**
- 数据一致性有保障
- 复制和恢复不会出错
- 磁盘空间充足

---

### 40. 什么是两阶段提交？请描述具体流程？

**两阶段提交**：保证 redo log 和 binlog 数据一致性的提交协议。

**流程**：
```
1. prepare 阶段
   └── 写 redo log，状态为 prepare

2. commit 阶段
   ├── 写 binlog
   └── 写 redo log，状态为 commit
```

**详细步骤**：
1. 事务进入 prepare 状态，写 redo log（prepare）
2. 事务执行器写 binlog
3. 事务提交，写 redo log（commit）
4. 完成

---

### 41. 两阶段提交能解决什么问题？为什么需要它？

**解决的问题**：保证 redo log 和 binlog 的数据一致性。

**为什么需要两阶段提交**：

| 场景 | 无两阶段提交 | 有两阶段提交 |
|------|-------------|-------------|
| 先写 redo log，再写 binlog | redo log 有记录，binlog 没有 → 主从不一致 | ✅ |
| 先写 binlog，再写 redo log | binlog 有记录，redo log 没有 → 崩溃恢复丢数据 | ✅ |

**崩溃恢复逻辑**：
- redo log prepare + binlog 有 → 提交
- redo log prepare + binlog 无 → 回滚

---

### 42. undo log 是什么？它有哪些类型？

**undo log（回滚日志）**：记录数据被修改前的值，用于回滚事务和实现 MVCC。

**undo log 类型**：

| 类型 | 说明 | 用途 |
|------|------|------|
| **Insert undo** | 记录 INSERT 操作 | 事务回滚 |
| **Update undo** | 记录 UPDATE/DELETE 操作 | 事务回滚、MVCC |

**undo log 存储位置**：
- 系统表空间（ibdata1）
- 独立的 undo tablespace（MySQL 5.7+）

---

## MySQL 事务

### 43. 什么是事务？事务有哪些特性（ACID）？

**事务**：一组原子性的 SQL 操作，要么全部执行成功，要么全部失败回滚。

**ACID 特性**：

| 特性 | 说明 | 实现机制 |
|------|------|----------|
| **原子性（Atomicity）** | 事务是最小执行单位，不可分割 | undo log |
| **一致性（Consistency）** | 事务前后数据保持一致 | 其他三个特性保证 |
| **隔离性（Isolation）** | 并发事务互不干扰 | 锁 + MVCC |
| **持久性（Durability）** | 事务提交后数据持久保存 | redo log |

---

### 44. MySQL 有哪四种隔离级别？默认是哪个？

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|------------|------|
| **READ UNCOMMITTED**（读未提交） | ✅ 可能 | ✅ 可能 | ✅ 可能 |
| **READ COMMITTED**（读已提交） | ❌ 不可能 | ✅ 可能 | ✅ 可能 |
| **REPEATABLE READ**（可重复读，默认） | ❌ 不可能 | ❌ 不可能 | ✅ 可能（InnoDB 通过 MVCC+Next-Key Lock 解决） |
| **SERIALIZABLE**（串行化） | ❌ 不可能 | ❌ 不可能 | ❌ 不可能 |

**Oracle 默认**：READ COMMITTED
**MySQL 默认**：REPEATABLE READ

---

### 45. 脏读、不可重复读、幻读分别是什么？有什么区别？

| 问题 | 说明 | 发生在 |
|------|------|--------|
| **脏读** | 读取到其他事务**未提交**的数据 | 读未提交隔离级别 |
| **不可重复读** | 同一事务两次读取同一行，结果不同（数据被修改） | 读已提交及以上 |
| **幻读** | 同一事务两次查询，记录数不同（数据被新增/删除） | 可重复读及以上 |

**区别**：
- 脏读：读取了**未提交**的数据
- 不可重复读：同一行数据被**修改**
- 幻读：**查询结果集**发生变化（新增/删除）

---

### 46. MySQL 是如何解决幻读问题的？

**MySQL InnoDB 通过两种机制解决幻读**：

1. **MVCC（多版本并发控制）**
   - 快照读：普通 SELECT，使用历史版本数据，避免幻读
   - 每次 SELECT 生成 ReadView（RC）或事务开始时生成（RR）

2. **Next-Key Lock（临键锁）**
   - 当前读：`SELECT...FOR UPDATE`、`INSERT`、`UPDATE`、`DELETE`
   - 锁定索引范围 + 记录本身
   - 阻止其他事务在范围内插入新记录

**RR 级别下**：
- 快照读：无幻读（MVCC）
- 当前读：无幻读（Next-Key Lock）

---

### 47. 什么是 MVCC？它是如何实现的？

**MVCC（Multi-Version Concurrency Control）**：多版本并发控制，通过保存数据的多个版本，实现读写不阻塞。

**核心思想**：
- 读操作不阻塞写操作
- 写操作不阻塞读操作
- 每个事务看到的是某个时间点的快照

---

### 48. MVCC 的核心组件有哪些？各自的作用是什么？

| 组件 | 说明 |
|------|------|
| **隐藏字段** | DB_TRX_ID（最近修改的事务ID）、DB_ROLL_PTR（指向 undo log 的指针）、DB_ROW_ID（隐藏主键） |
| **undo log** | 记录数据的历史版本，形成版本链 |
| **ReadView** | 记录活跃事务 ID 列表，判断数据版本可见性 |

**版本链结构**：
```
当前数据 → undo log(版本1) → undo log(版本2) → ...
```

---

### 49. ReadView 是什么？RC 和 RR 隔离级别下有什么区别？

**ReadView**：事务快照，包含活跃事务 ID 列表（m_ids）和相关事务 ID。

**可见性判断规则**：
1. 数据事务 ID < m_ids 中最小值 → 可见
2. 数据事务 ID 在 m_ids 中 → 不可见
3. 数据事务 ID >= max_id → 可见

**RC 和 RR 的区别**：

| 隔离级别 | ReadView 生成时机 | 同一事务两次 SELECT 结果 |
|----------|------------------|------------------------|
| **READ COMMITTED** | 每次 SELECT 都生成新 ReadView | 可能不同 |
| **REPEATABLE READ** | 事务第一次 SELECT 时生成 | 始终相同 |

---

### 50. 什么是快照读和当前读？它们有什么区别？

| 类型 | 说明 | 锁 |
|------|------|---|
| **快照读** | 普通 SELECT 语句，读取历史版本数据 | 无锁，利用 MVCC |
| **当前读** | SELECT...FOR UPDATE、INSERT、UPDATE、DELETE | 加锁 |

**快照读示例**：
```sql
SELECT * FROM tb WHERE id = 1;  -- 快照读
```

**当前读示例**：
```sql
SELECT * FROM tb WHERE id = 1 FOR UPDATE;  -- 当前读，加 X 锁
INSERT INTO tb VALUES (...);  -- 当前读，加 X 锁
UPDATE tb SET ... WHERE id = 1;  -- 当前读，加 X 锁
```

---

### 51. MySQL 的隔离级别是基于锁实现的吗？

**不完全是**。

**快照读**：基于 MVCC 实现，无锁
**当前读**：基于锁实现

**不同隔离级别的实现**：

| 隔离级别 | 快照读 | 当前读 |
|----------|--------|--------|
| READ UNCOMMITTED | 无 MVCC，直接读最新 | 行锁 |
| READ COMMITTED | MVCC（每次生成新 ReadView） | 行锁 |
| REPEATABLE READ | MVCC（事务级别 ReadView） | 行锁 + 临键锁 |
| SERIALIZABLE | MVCC 或 锁 | 全表锁 |

**注意**：InnoDB 在 RC/RR 级别下，快照读基于 MVCC，当前读基于锁。

---

## MySQL 锁

### 52. 表级锁和行级锁有什么区别？各自适用于什么场景？

| 类型 | 粒度 | 开销 | 并发度 | 适用场景 |
|------|------|------|--------|----------|
| **表级锁** | 整张表 | 小 | 低 | 全表扫描、批量操作、MyISAM |
| **行级锁** | 单行/多行 | 大 | 高 | InnoDB 高并发场景 |

**InnoDB 表级锁场景**：
- 表级别操作（ALTER TABLE、LOCK TABLE）
- 非索引字段的 WHERE 条件

---

### 53. InnoDB 有哪些行锁类型？有什么区别？

| 类型 | 说明 | 锁定范围 |
|------|------|----------|
| **记录锁（Record Lock）** | 锁定单个行记录 | 单行 |
| **间隙锁（Gap Lock）** | 锁定范围，不包括记录本身 | 索引间隙 |
| **临键锁（Next-Key Lock）** | Record Lock + Gap Lock | 行 + 前后间隙 |

**示例**：
- `SELECT * FROM tb WHERE id = 10 FOR UPDATE;` → Record Lock
- `SELECT * FROM tb WHERE id BETWEEN 5 AND 15 FOR UPDATE;` → Gap Lock + Record Lock = Next-Key Lock

---

### 54. 什么是临键锁（Next-Key Lock）？它解决什么问题？

**Next-Key Lock = Record Lock + Gap Lock**

**解决的问题**：幻读

**示例**：
```sql
-- 假设表有 id: 1, 5, 10
-- 执行：SELECT * FROM tb WHERE id <= 10 FOR UPDATE;

-- 锁定的范围：
-- (-∞, 1], (1, 5], (5, 10], (10, +∞)
```

**在 RR 级别下**：临键锁阻止其他事务在锁定范围内插入新记录，从而解决幻读。

---

### 55. 什么是间隙锁（Gap Lock）？

**Gap Lock**：锁定索引之间的间隙，不包括记录本身。

**特点**：
- 只在 RR 隔离级别下生效
- 目的是防止幻读
- 间隙锁之间不互斥（可以锁定重叠的间隙）
- 唯一索引或等值查询时，Gap Lock 可能退化为 Record Lock

**示例**：
- 索引 id 有值：1, 5, 10
- `SELECT * FROM tb WHERE id = 7 FOR UPDATE;` 锁定 (5, 10) 间隙

---

### 56. 共享锁和排他锁的区别是什么？

| 类型 | 别名 | 作用 | 获取条件 |
|------|------|------|----------|
| **共享锁（S）** | 读锁 | 允许其他事务获取 S 锁 | SELECT...LOCK IN SHARE MODE |
| **排他锁（X）** | 写锁 | 排斥其他所有锁 | SELECT...FOR UPDATE、INSERT、UPDATE、DELETE |

**兼容矩阵**：

|  | S 锁 | X 锁 |
|--|------|------|
| **S 锁** | ✅ 兼容 | ❌ 互斥 |
| **X 锁** | ❌ 互斥 | ❌ 互斥 |

---

### 57. 意向锁有什么用？IS 和 IX 锁的作用分别是什么？

**意向锁**：表级锁，表示事务有意向对某些行加锁。

| 类型 | 说明 | 作用 |
|------|------|------|
| **IS 锁** | 意向共享锁 | 事务有意向对某些行加 S 锁 |
| **IX 锁** | 意向排他锁 | 事务有意向对某些行加 X 锁 |

**为什么需要意向锁**：
- 快速判断表是否有行锁（无需遍历所有行）
- 配合表级锁实现锁升级（如 LOCK TABLE 会检查 IS/IX）

**兼容矩阵**：

|  | IS | IX | S | X |
|--|----|----|---|---|
| **IS** | ✅ | ✅ | ✅ | ❌ |
| **IX** | ✅ | ✅ | ❌ | ❌ |
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |

---

### 58. 什么是自增锁？它有哪几种模式？

**自增锁（AUTO-INC Lock）**：表级锁，用于自增主键的分配。

**模式**（`innodb_autoinc_lock_mode`）：

| 模式 | 说明 | 特点 |
|------|------|------|
| **0**（传统） | 传统模式，使用 AUTO-INC 锁 | 串行，可预测 |
| **1**（连续） | 轻量级锁，批量分配后释放（MySQL 8.0 前默认） | 并发较好 |
| **2**（交错） | 互斥锁彻底移除（MySQL 8.0 后默认） | 并发最高，主从可能不一致 |

**建议**：主从复制场景建议用模式 1，避免自增 ID 不连续。

---

### 59. 什么是死锁？如何避免？

**死锁**：两个或多个事务相互等待对方持有的锁，形成循环等待。

**死锁的四个必要条件**（缺一不可）：
1. 互斥
2. 占有且等待
3. 不可抢占
4. 循环等待

**避免死锁的方法**：

1. **固定顺序访问表**（同一业务，按相同顺序操作数据）
2. **减少锁持有时间**（尽快提交事务）
3. **降低隔离级别**（但可能引发其他问题）
4. **使用低隔离级别** + **索引**（减少锁定范围）
5. **添加合理索引**（减少锁定行数）

**MySQL 处理死锁**：
- InnoDB 自动检测死锁
- 回滚 undo log 最小的事务
- 返回 "Deadlock found" 错误

### 61. EXPLAIN 执行计划有哪些关键字段？

| 字段 | 说明 |
|------|------|
| **id** | 查询序号，id 越大越先执行 |
| **select_type** | 查询类型（SIMPLE、PRIMARY、SUBQUERY 等） |

| **key_len** | 索引长度 |
| **rows** | 预估扫描行数 |
| **Extra** | 额外信息（Using index、Using filesort 等） |

### 62. type 字段有哪些值？哪些是优化的？哪些需要优化？

**type 值从好到坏**：

| type | 说明 | 是否优化 |
|------|------|----------|
| **system** | 系统表，只有单行 | ✅ 最优 |
| **const** | 主键或唯一索引等值查询，最多一行 | ✅ |
| **eq_ref** | 唯一索引等值扫描，返回所有匹配行 | ✅ |
| **ref** | 非唯一索引等值扫描 | ✅ |
| **range** | 索引范围扫描（>、<、BETWEEN、IN） | ⚠️ 可接受 |
| **index** | 全索引扫描 | ⚠️ 可接受 |
| **ALL** | 全表扫描 | ❌ 需优化 |

**优化目标**：至少 ref/range，避免 ALL。

### 63. Extra 字段出现 Using filesort 或 Using temporary 意味着什么？

| Extra | 含义 | 是否需优化 |
|-------|------|------------|
| **Using filesort** | 文件排序（内存或磁盘），无法利用索引 | ❌ 需优化 |

| **Using index** | 覆盖索引，无需回表 | ✅ 好 |
| **Using index condition** | 索引下推（ICP） | ✅ 好 |
| **Using where** | Server 层过滤 | ⚠️ 需结合情况 |

**优化方法**：

```sql
-- 避免 filesort：添加合适索引，或优化 ORDER BY

```

### 64. 有哪些常见的 SQL 优化手段？

1. **避免 SELECT ***
2. **使用具体字段代替 SELECT ***
3. **避免子查询，改用 JOIN**（MySQL 5.7+ 优化器已改进）
4. **OR 改用 IN（不超过 500 个）**
5. **避免 ORDER BY RAND()**

7. **批量操作代替循环单条**
8. **分解大查询**：化大为小
9. **增加索引**：针对 WHERE 条件添加索引
10. **覆盖索引**：减少回表

### 65. 深分页如何优化？

**深分页问题**：`LIMIT 10000, 10` 需要跳过 10000 条数据。

**优化方法**：

1. **延迟关联**：先查主键，再关联查询
```sql
-- 原查询
SELECT * FROM tb ORDER BY id LIMIT 10000, 10;

-- 优化：延迟关联
SELECT t.* FROM tb t
INNER JOIN (
    SELECT id FROM tb ORDER BY id LIMIT 10000, 10
) AS t2 ON t.id = t2.id;
```

2. **书签式分页**：记录上一页最后一条 ID
```sql
-- 第一页
SELECT * FROM tb ORDER BY id LIMIT 10;
-- 第二页
SELECT * FROM tb WHERE id > last_id ORDER BY id LIMIT 10;
```

3. **子查询利用覆盖索引**：
```sql
SELECT * FROM tb WHERE id IN (
    SELECT id FROM tb ORDER BY id LIMIT 10000, 10
);
```

### 66. 为什么不要使用 SELECT * ？有什么替代方案？

**SELECT * 的问题**：

1. **增加网络带宽**：传输不需要的字段
2. **无法使用覆盖索引**：优化受限
3. **增加 CPU 消耗**：解析更多字段
4. **表结构变更时出错**：字段顺序变化可能导致程序 bug
5. **可维护性差**：无法明确看到需要哪些字段

**替代方案**：只查询需要的字段
```sql
-- 不推荐
SELECT * FROM tb WHERE id = 1;

-- 推荐
SELECT id, name, age FROM tb WHERE id = 1;
```

### 67. ORDER BY RAND() 有什么问题？如何优化？

**问题**：
- 需要随机排序所有记录
- 无法利用索引
- 数据量大时性能极差（O(n)）

**优化方法**：

1. **主键随机法**：
```sql
SELECT * FROM tb WHERE id >= (SELECT FLOOR(RAND() * (SELECT MAX(id) FROM tb))) LIMIT 1;
```

2. **应用层生成随机 ID**：在代码中生成随机 ID，再查询

3. **预先随机化**：增加一列 `rand_value`，查询时 ORDER BY rand_value

4. ** LIMIT N 随机**：适用于只需要少量随机记录
```sql
SELECT * FROM tb ORDER BY RAND() LIMIT 1;
```

### 68. 什么是批量插入？如何优化大量数据的插入？

**批量插入**：将多条 INSERT 语句合并为一条。

**优化方法**：

1. **批量 INSERT**：
```sql
-- 原：单条插入
INSERT INTO tb VALUES (1, 'a');
INSERT INTO tb VALUES (2, 'b');

-- 优化：批量插入
INSERT INTO tb VALUES (1, 'a'), (2, 'b'), (3, 'c');
```

2. **事务包装**：每 1000-5000 条提交一次
```sql
START TRANSACTION;
INSERT INTO tb VALUES (...);  -- 批量
COMMIT;
```

3. **关闭唯一检查和外键检查**：
```sql
SET UNIQUE_CHECKS = 0;
SET FOREIGN_KEY_CHECKS = 0;
-- 批量插入
SET UNIQUE_CHECKS = 1;
SET FOREIGN_KEY_CHECKS = 1;
```

4. **LOAD DATA INFILE**（最快）：
```sql
LOAD DATA INFILE '/tmp/data.csv' INTO TABLE tb;
```

### 70. MySQL 主从复制原理是什么？

**原理图**：
```
┌─────────────┐     binlog      ┌─────────────┐     relay log     ┌─────────────┐
│   Master    │ ──────────────→ │    Slave    │ ←─────────────── │ Relay Log  │
│  (写数据)   │                 │  (读 binlog)│                  │  (本地)     │
└─────────────┘                 └─────────────┘                  └─────────────┘
                                        ↓
                                  SQL Thread 执行
```

**复制步骤**：
1. Master 写入数据，binlog 记录变更
2. Slave 的 IO Thread 连接 Master，请求 binlog
3. Master 的 Binlog Dump 发送 binlog 给 Slave
4. Slave 的 IO Thread 写入 relay log
5. Slave 的 SQL Thread 读取 relay log，执行 SQL

**复制方式**：
- **异步复制**：默认，Master 不等待 Slave
- **半同步复制**：至少一个 Slave 确认
- **全同步复制**：所有 Slave 确认

### 71. 读写分离有什么作用？如何实现？

**读写分离的作用**：
- 减轻主库压力（读操作分流到从库）
- 提高系统吞吐能力
- 从库提供备份，保障数据安全

**实现方式**：

1. **应用层实现**（代码层面）：
   - 写操作 → 主库
   - 读操作 → 从库
   - 使用 Sharding-JDBC、Druid 等

2. **中间件实现**：
   - MySQL Proxy、Atlas、ShardingSphere-Proxy
   - 对应用透明

**注意问题**：
- 主从延迟导致读写不一致
- 解决方案：强制走主库读、延迟感知、选择性读从库

### 72. 分库分表适用于什么场景？有什么优缺点？

**适用场景**：
- 单表数据量过大（超过千万级）
- 单库并发瓶颈
- 数据需要长期保留（如历史数据归档）

**分库分表方式**：

| 方式 | 说明 | 特点 |
|------|------|------|
| **垂直分库** | 按业务拆分到不同库 | 减少跨库 JOIN |
| **垂直分表** | 按字段拆分大表 | 减少单表字段数 |
| **水平分库** | 数据分到不同库 | 库间数据独立 |
| **水平分表** | 数据分到同库不同表 | 单表数据减少 |

**优点**：
- 突破单表/单库性能瓶颈
- 提升并发能力
- 便于历史数据归档

**缺点**：
- 跨库 JOIN 困难
- 分布式事务复杂
- 扩容复杂度高
- 运维成本增加

### 75. 如果让你设计一个数据库表，你会考虑哪些方面？
