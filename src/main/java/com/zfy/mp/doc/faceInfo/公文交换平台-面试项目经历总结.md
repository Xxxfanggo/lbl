## 一、精简版（可直接放简历）

### 项目名称

政务公文交换平台（2023.xx – 202x.xx）

### 技术栈一行版

Java 11 / Spring Boot 2.7 / Spring Cloud Gateway / Spring Cloud Alibaba（Nacos）/ OpenFeign / MyBatis-Plus / Redis（Redisson）/ OAuth2 + Spring Security / XXL-Job / RocketMQ / MinIO / OFD 版式文件 / 达梦、人大金仓、openGauss 等国产数据库

### 项目描述（简历版，约 120 字）

面向政府单位的公文交换平台，实现跨单位公文的拟稿、发布、交换、签收、回执、催办、转发与撤回的全生命周期管理。平台采用 Spring Cloud 微服务架构，由网关、系统管理、基础设施、公文交换、简报上传、前置机同步 6 个服务组成，支持 OFD 版式文件转换、多租户隔离、灰度发布与国产数据库适配，服务于【XX】家单位的日常公文流转。

### 主要职责（发文方向，可挑 4–6 条）

- 负责发文核心模块的设计与开发，实现公文「拟稿 → 暂存 → 定时发布 → 已发布 → 归档/撤回」的状态机流转；发布时按主送单位批量生成收文记录，并支持补发、再发、退回等异常流程。
- 负责与公文交换前置平台的对接：将公文元数据与附件组装为标准 XML 信封（JAXB 序列化），通过 HTTP + Bearer Token 异步推送（@Async），并实现 AccessToken 本地缓存与到期前 60 秒主动刷新，减少认证开销。
- 设计 OFD 版式文件异步转换机制：上传附件后进入转换队列，定时任务（cron 每 3 分钟）分页扫描未转换/转换失败的附件并自动重试，转换状态（UNDO/SUCCESS/FAIL）全程可追踪，转换能力可通过配置开关降级。
- 实现公文多级转发与递归撤回：通过转发关系表记录转发层级（forwardLevel）形成转发树，撤回时递归遍历转发链路、批量回收各级收文并保证事务一致性。
- 实现细粒度公文安全管控：下载/打印/转发次数限制（DC/PC 控制位）、机要白名单校验、签收回执与经办留痕；针对特急/特提公文及超期未签收场景，自动触发邮件 + 站内催办通知。
- 基于平台框架能力完成业务落地：OAuth2 统一认证、多租户数据隔离、MyBatis-Plus 联表深度查询（MPJ）优化关联加载、Knife4j 接口文档、操作日志审计；参与国产数据库（达梦/人大金仓）兼容性适配与验证。

## 二、详细版（面试复习用）

### 1. 项目背景

政府单位之间传统公文流转依赖纸质交换或孤立的 OA 系统，存在时效低、不可追溯、密级管控难的问题。本平台为区域内各委办局提供统一的电子公文交换枢纽：发文单位在平台上拟稿发布，平台将公文以标准格式分发至各主送/抄送单位，接收单位在线签收、回执、转发，全过程留痕可审计。政务场景对平台提出了三类特殊要求：**OFD 版式文件**（国家标准 GB/T 33190-2016 的电子公文格式）、**国产化信创适配**（达梦、人大金仓、openGauss 数据库）、**密级与扩散管控**（下载/打印/转发次数限制、机要白名单）。

### 3. 我负责的发文模块：核心业务链路

**完整链路**：拟稿创建 → 暂存/提交 → （定时）发布 → 按主送单位生成收文 → XML 组包交换发送 → 对端签收/回执 → 催办/撤回/转发

关键类与代码位置（包路径 `com.wondersgroup.module.official.document`）：

| 步骤      | 关键类#方法                                                        | 说明                                    |
| ------- | ------------------------------------------------------------- | ------------------------------------- |
| 创建发文    | `OutgoingDocumentServiceImpl#generateOutgoingDocument`        | 创建发文记录，级联创建公文主表、主送单位、附件               |
| 发布      | `OutgoingDocumentServiceImpl#publishOutgoingDocument`         | 状态流转为 PUBLISHED，支持设定 publishDate 定时发布 |
| 生成收文    | `OutgoingDocumentServiceImpl#handleOfficialDocumentPublished` | 遍历主送单位批量创建 ReceivingDocument          |
| 交换发送    | `service.exchange.impl.DocumentSendMethodServiceImpl#send`    | 构建 XML 信封 + 附件清单，逐单位发送                |
| XML 序列化 | `BaseDocumentMethodServiceImpl#marshallerToXml`               | JAXB Marshaller                       |
| HTTP 推送 | `BaseDocumentMethodServiceImpl#ExchangeData`（@Async）          | URLEncode 后 POST 到交换平台 API            |
| 撤回      | `OutgoingDocumentServiceImpl#retractOutgoingDocument`         | 递归处理转发链，批量回收                          |
| 转发      | `ForwardDocumentServiceImpl#forwardDocument`                  | 收文单位向下级转发                             |
| OFD 转换  | `OfficicalDocumentAttachmentConvertService`                   | 队列 + @Scheduled(cron 每 3 分钟) 扫描重试     |
| 定时任务    | `scheduler.OutgoingDocumentTask`                              | 定时发布、签收提醒、催办通知                        |

**核心表设计**（10 张左右）：发文表（OUTGOING_DOCUMENT）、公文主表（OFFICIAL_DOCUMENT，含标题/文号/密级/紧急程度/状态）、主送单位表（含下载/打印/转发次数配额）、收文表（RECEIVING_DOCUMENT，每个主送单位一条，含签收状态与管控位）、附件表（含 OFD_CONVERT_STATUS）、转发关系表（FORWARD_DOCUMENT，记录 forwardLevel 与上下级发文 ID）、回执表、经办记录表、清退/审批单表、打印号表（按单位独立自增）。

**关键关系**：一份发文 → 一条公文主记录 → N 条收文（按主送单位）→ 每条收文可再转发生成新发文（树形结构）→ 回执与经办记录全程挂接。

### 4. 技术难点与亮点（面试重点讲这几个）

**① 公文状态机与定时发布**
状态枚举 STAGING（暂存）→ PUBLISHING（待发布）→ PUBLISHED（已发布）→ ARCHIVE（归档）/ RECYCLE（已撤回），配合接收维度状态 receiveStatus（PART/ALL/RECYCLE）。状态以枚举 + 自定义 MyBatis TypeHandler（`OfficialDocumentStateEnumTypeHandler`）持久化，避免魔法值散落。拟稿时可设定 publishDate，由定时任务扫描到点自动发布。讲述要点：为什么用状态机思维（状态迁移收敛在 Service 层、非法迁移直接拒绝）、定时发布与人工发布共用同一发布入口保证逻辑一致。

**② 与交换平台的 HTTP + XML 异步对接**
公文以标准 XML 信封（信封头 + 公文元数据 + 附件清单）通过 JAXB 序列化，HTTP POST 推送到前置交换平台，认证采用 OAuth2 风格的 AccessToken：本地 HashMap 缓存 token，到期前 60 秒主动换新，避免每次请求都走认证。发送方法标注 @Async 异步化，发布主流程不被网络 IO 阻塞。面试讲述要点：为什么不用 MQ —— 对端是政务外网的标准交换前置机，协议是规定好的 HTTP+XML 报文（含签收、退回、催办、补发、再发、回收等十余种报文类型，见 front-synchronous 模块的 Representation 类），不是我们能选型的；MQ（RocketMQ）保留在平台框架层用于内部解耦。

**③ OFD 版式文件异步转换**
政务公文正文必须是 OFD 版式（不可随意编辑、可签章）。附件上传时若非 OFD，记录转换状态 UNDO 并加入转换队列；`@Scheduled(cron = "0 0/3 * * * ?")` 每 3 分钟分页（每批 50 条）扫描未转换附件入队重试，失败状态 FAIL 的 12 小时内自动重捞；转换功能有配置开关（documentCovertProperties.enabled）可整体降级。文件转换底层由框架 file 组件封装的数科（Suwell）OFD 转换库完成。讲述要点：异步化原因（转换耗时秒级，不能阻塞上传）、幂等（convertItemMap 按附件 ID 去重防止重复入队）、可观测（状态字段可查询转换进度）。

**④ 多级转发与递归撤回**
收文单位可将公文向下级单位转发，转发会生成新的发文记录并通过转发关系表（oldOutgoingDocumentId + forwardLevel）形成转发树。撤回时 `findNeedRecycleDocuments` 递归收集整棵转发树上的发文/收文 ID，批量更新为 RECYCLE 并在同一事务内提交。讲述要点：递归终止条件、批量更新代替逐条循环更新、事务边界（@Transactional 包住整个撤回链路）。

**⑤ 细粒度安全管控（政务特色）**
每个主送单位可独立配置：允许下载次数（DC）、允许打印次数（PC）、允许转发份数；下载走 `ExchangeFileController#downloadFile`，校验 domain 匹配 → 单位权限 → 剩余次数，超限拒绝。机要件走白名单（机要交通员角色）校验。打印号按单位独立自增（打印号表），保证纸质份号可追溯。

**⑥ 催办与差异化通知**
特急/特提（emergencyDegree）或勾选"需催办"的公文，发布时即向接收单位的交换员/签收员角色组发送邮件；定时任务扫描超期未签收的收文，自动触发邮件 + 站内信催办。

**⑦ 平台层亮点（体现广度，适合全栈/架构追问）**
网关灰度发布（自定义 GrayReactiveLoadBalancerClientFilter + GrayLoadBalancer，按版本标签路由，配合 grayLb:// 协议实现金丝雀发布）；多租户（ThreadLocal 上下文 + MyBatis 拦截器自动拼租户条件 + Redis Key 前缀隔离 + Feign/MQ 链路透传）；服务保障（Redis 分布式限流切面、@Idempotent 幂等注解、Lock4j+Redisson 分布式锁、API 签名校验）；文件存储抽象（FileClient 接口 + Local/DB/FTP/SFTP/S3/MinIO 六种实现，配置切换）；国产化（MySQL/达梦 DM8/人大金仓/openGauss/Oracle/PG/SQLServer 七种驱动适配，BouncyCastle 支持国密算法）；可观测性（SkyWalking 链路追踪 + Prometheus 指标 + Spring Boot Admin）。

### 5. 面试高频追问与回答要点

**Q1：公文交换为什么用 HTTP+XML 而不用消息队列？**
对接的是政务交换前置机，报文格式（XML 信封）和通信方式（HTTP + Token）是上级平台的标准规范，接入方没有选型权；XML 报文类型覆盖发送/签收/退回/催办/补发/再发/回收等完整交互语义。内部服务间解耦仍可用 RocketMQ（框架层已集成）。可以补充：如果让我重新设计内部链路，发布后"生成收文+组包发送"可以改成事务消息驱动，提高吞吐并天然解决重试。

**Q2：发送失败/重复发送怎么办（幂等与重试）？**
发送异步化后通过交换记录状态追踪结果；交换平台侧以 exchangeId 判重（sendExchangeId 字段保存平台返回的交换 ID），重复推送不会生成重复收文；框架层另有 @Idempotent 注解（Redis 去重）用于接口防重。OFD 转换失败有定时重捞重试。诚实回答边界：当时没有做完整的本地消息表/对账机制，这是可改进点。

**Q3：撤回的事务一致性怎么保证？转发树很深怎么办？**
单库内递归收集 ID 后批量 UPDATE，整体包在一个事务里；转发层级实际业务中通常 2–3 级，递归深度可控。如果跨库/跨服务，需要引入补偿（撤回通知报文本身就是一种最终一致性手段——对端收到 RECYCLE 报文后回收本侧收文）。

**Q4：OFD 是什么？为什么必须转 OFD？**
OFD（Open Fixed-layout Document）是中国版式文档国家标准（GB/T 33190-2016），政务公文要求版式固定、防篡改、支持电子签章，相当于"国产 PDF"。平台用数科（Suwell）的转换引擎把 doc/docx/wps 等转成 OFD。

**Q5：多租户怎么实现的？**
请求头携带租户 ID → 网关/Web 过滤器写入 ThreadLocal（TenantContextHolder）→ MyBatis 拦截器（TenantDatabaseInterceptor）对 SQL 自动追加租户 where 条件 → Redis 缓存按租户加 Key 前缀 → Feign 拦截器、MQ Hook 在跨服务/异步链路透传租户上下文；@TenantIgnore 注解可豁免系统级查询。

**Q6：网关层做了什么？灰度发布怎么实现？**
Spring Cloud Gateway（WebFlux 响应式）：Token 鉴权过滤器（SmartTokenAuthenticationFilter，校验 OAuth2 token、带缓存）、访问日志、CORS；灰度通过自定义 ReactiveLoadBalancer，根据请求特征（如版本头）从 Nacos 实例列表中筛选对应版本实例，实现新版本小流量验证。

**Q7：MyBatis-Plus 联表深度查询（MPJ）解决什么问题？**
公文详情需要同时加载主送单位、抄送单位、附件等多个子表，传统写法要么 N+1 查询要么手写大 SQL；mybatis-plus-join 的 getByIdDeep 一次性级联加载关联实体，代码量小且可维护。

**Q8：认证授权链路？**
前端登录 → system 服务（OAuth2TokenApiImpl）颁发 AccessToken（存 Redis）→ 网关过滤器统一校验 → 通过后将用户上下文放入请求头传给下游 → 下游服务经 security 组件的 TokenAuthenticationFilter/LoginUserRequestInterceptor 还原登录用户；角色权限基于 RBAC（用户-角色-菜单/按钮权限），数据行级权限由 data-permission 组件的 SQL 拦截实现。

**Q9：国产数据库适配踩过什么坑？**（按实际经历挑选）
可讲方向：达梦/金仓的关键字冲突与大小写敏感、分页方言差异、LocalDateTime 等类型映射（项目里有自定义 LocalDateTypeHandler）、批量插入语法差异；适配思路是 MyBatis-Plus 方言 + 自定义 TypeHandler + 避免数据库特有函数。

**Q10：你这个模块的性能瓶颈在哪？怎么优化？**
附件转换与交换发送是 IO 密集环节 → 全部异步化；列表查询走联表索引 + 分页；附件下载直接走文件服务流式输出。可以坦诚说明政务场景并发量不极端，设计上更偏重**可靠性与可追溯**而非高并发。
