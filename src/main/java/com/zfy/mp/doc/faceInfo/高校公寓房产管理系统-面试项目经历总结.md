## 一、精简版（可直接放简历）

### 项目名称

高校公寓与房产综合管理系统（上海交通大学）（20xx.xx – 20xx.xx）

### 技术栈一行版

Java 8 / Spring Boot / Spring MVC / MyBatis-Plus / Shiro + JWT / Redis / Quartz / Druid 多数据源（MySQL、SQL Server、Oracle）/ POI（Excel）/ Swagger2 / 交大 InfoPlus 流程平台

### 项目描述（简历版，约 120 字）

为上海交通大学资产与房产管理部门建设的综合管理系统，覆盖教师公寓全生命周期管理（资格申请、公示、选房、协议签署、入住、租金收缴、续租、退房）及校园房产资产管理（楼宇/房间台账、维修、物业合同）。系统由业务主系统（Spring Boot 单体）与流程对接服务（对接交大 InfoPlus 流程平台，承载近 40 类审批流程回调）两部分组成，服务全校教职工【XX】人、管理房源【XX】间。

### 主要职责（公寓模块，可挑 4–6 条）

- 负责教师公寓模块的设计与开发，实现「资格申请 → 多级审核 → 公示 → 选房 → 协议签署 → 入住（门禁下发）→ 租金收缴 → 续租/换房 → 退房」全生命周期业务闭环，支持初始申请、续租、换房、正式资格、编制变更 5 类申请的差异化审批逻辑。
- 负责与交大 InfoPlus 流程平台的对接：业务侧封装统一的 SjtuWorkFlowService（流程发起、审核意见留存、实例查询），流程侧基于 Messenger 回调模式开发选房、续租、协议签署、退宿等公寓类流程的事件处理器（全系统共注册 39 个流程回调 Bean）。
- 实现续租资格自动校验引擎：组合多个查询条件链（申请状态、协议到期窗口、累计居住年限上限、特殊房源限制），校验时间窗口通过 Quartz 参数表配置化，大幅减少公寓办人工初筛工作量。
- 设计「校区 → 楼宇 → 楼栋 → 楼层 → 房间」五级房源级联体系，采用 Redis Hash 按层级缓存字典数据，前端级联下拉直接读缓存，避免高频数据库查询。
- 实现基于角色的数据权限分级：院系领导仅见本院申请数据，物业人员按等级（校区经理/楼宇经理）动态限定可管理的楼宇与房间范围。
- 实现房间拆分/合并功能（含流程审批）：拆分时自动生成房间编码并校验房间号唯一性，合并时级联处理旧房源数据，操作全程留痕并同步刷新 Redis 缓存；另负责申请数据 Excel 批量导入导出（POI）。

## 二、详细版（面试复习用）

### 1. 项目背景

高校教师公寓资源紧张、申请审批环节多（院系、人事处、资产与实验室处等多部门会签）、政策规则复杂（不同人才类别对应不同公寓类型与租住年限上限）。传统线下办理周期长、公示流程不透明、房源台账与实际不符。本系统将公寓业务全流程线上化，并与学校统一的 InfoPlus 流程平台（form.sjtu.edu.cn）打通审批，与门禁、财务等系统联动，实现"申请—审批—公示—选房—签约—入住—收租—退房"闭环管理。

### 4. 技术难点与亮点（面试重点讲这几个）

**① 续租资格自动校验引擎**
续租是公寓业务里规则最复杂的场景：要同时校验申请状态链（排除已驳回/已终止）、协议是否进入可续租时间窗口（距到期 T 天内，T 从 Quartz 参数表 `ScheduleUtils.getScheduleMap("XZSQTJSJ")` 读取，可配置）、累计居住年限是否超过该公寓类型上限（`rentPaymentService.getTotalFavorMonths()` 按实缴月份累计）、特殊房源限制（短租公寓、待征收楼栋不可续租）、代申人场景（ifApplyOther）。实现上用多个 MyBatis-Plus EntityWrapper 组合 AND/OR 条件链逐层过滤。讲述要点：把审批政策"翻译"为可配置参数 + 查询条件链，政策调整只改参数不改代码。

**② InfoPlus 流程平台双向集成（跨系统状态一致性）**
正向：业务系统封装 `SjtuWorkFlowService.startWorkFlow()` 统一发起流程，流程实例 ID 落库（SjtuWorkFlowEntity）与业务单据关联；逆向：InfoPlus 流程每个节点动作（通过/驳回/完成）回调 sjtu-workflow 的对应 Messenger（如 ApplyMessenger、RenewApplyMessenger、ApartmentAgreementMessenger 等，全系统注册 39 个），Messenger 再回写业务表状态并触发后续动作（驳回发邮件 `EmailUtils.apartmentSendNotice()`）。讲述要点：业务状态（approvalState）与流程状态通过实例 ID 关联、每步审核意见双侧留存、回调幂等处理。

**③ 五级房源级联 + Redis 缓存**
校区→楼宇→楼栋→楼层→房间五级结构，级联下拉框是全系统最高频查询。方案：按层级用 Redis Hash 缓存（`ConstantCode:HOUSE_DAILY_LIST:{campusId}`、`FLOOR_DAILY_LIST:{buildingId}`、`ROOM_LIST:{floorId}`），房间增删改（含拆分/合并）时同步失效对应缓存。`RoomController#listForCampusRoomCascader`（L228-374）。

**④ 房间拆分/合并（资产台账一致性）**
房间拆分（`RoomController#split` L865-929）：校验新房间号同层唯一 → 按楼层规则生成房间编码 → 写拆分留痕记录（ROOM_SPLIT）→ 刷新缓存；合并类似（ROOM_MERGE），且拆分/合并可走流程审批（`#adjustByFlow`）。难点是多步操作的事务一致性与缓存同步。

**⑤ 数据权限分级**
院系领导/公寓办负责人查询自动过滤本部门数据；物业人员按等级控权——校区经理（PROPERTY_LEVEL_01）见全校区、楼宇经理（PROPERTY_LEVEL_02）只见名下楼宇（PropertyPersonEntity 维护人员-楼宇映射），查询时动态拼接权限范围。

**⑥ Quartz 任务平台化**
任务持久化到 schedule_job 表，后台界面支持新增/暂停/恢复/立即执行，执行日志（schedule_job_log）记录耗时与失败原因；`ScheduleJob` 标注 `@DisallowConcurrentExecution` 防止同任务并发、`@PersistJobDataAfterExecution` 持久化任务数据。公寓侧应用：公示定时触发、续租窗口参数管理。

**⑦ 平台公共能力**
Shiro + JWT 认证（自定义 OAuth2Filter 从 header 取 token → OAuth2Realm 完成认证授权，方法级 `@RequiresPermissions("teacher_apartment:apartment:...")` 控权）；`@SysLog` 注解 + AOP 切面记录操作日志；`@RestControllerAdvice` 统一异常处理（业务异常/流程异常/重复键分类响应）；Druid 多数据源（master/slave/etl/jq，DataSourceAspect + ContextHolder 动态路由）；XSS/SQL 注入过滤器；Freemarker 代码生成器。

### 5. 面试高频追问与回答要点

**Q1：为什么拆成 shjd-sys 和 sjtu-workflow 两个工程？**
InfoPlus 是学校统一流程平台，对接需引入其 SDK 并暴露回调端点，且学校对回调服务的部署形态（WAR/Tomcat、网络位置）有要求；把流程适配独立成服务，业务系统不直接依赖 InfoPlus SDK，流程平台升级或更换时业务侧无感。这其实是防腐层（ACL）思想。

**Q2：业务状态和流程状态怎么保持一致？流程回调失败怎么办？**
流程实例 ID 与业务单据 ID 双向关联落库；每个审批节点动作通过 Messenger 回调更新业务状态，审核意见同时存业务侧（SjtuWorkFlowEntity）。回调失败的兜底：业务侧可通过实例 ID 主动查询流程平台状态对账。诚实边界：当时没有做自动对账任务，依赖人工核查 + 主动查询接口，可作为改进点讨论（本地消息表/定时对账）。

**Q3：Shiro 和 JWT 怎么配合的？和 Spring Security 比呢？**
登录成功后用 jjwt 签发 token（7 天有效期），前端每次请求带 token header；自定义 OAuth2Filter 拦截请求提取 token 构造 OAuth2Token，交给 OAuth2Realm 校验并加载用户权限（菜单/按钮权限串），方法上用 @RequiresPermissions 做细粒度控权。对比：Shiro 轻量、概念少、易上手，适合单体；Spring Security 与 Spring 生态（OAuth2/网关）整合更深，后来的公文交换平台微服务项目我们用的就是 Spring Security + OAuth2。

**Q4：续租校验为什么不放到流程平台里做？**
资格规则依赖业务库数据（缴费记录、协议、房源属性），流程平台只做审批编排不做业务计算；校验前置在业务系统还能在提交前即时反馈，不合格申请根本不进流程，减少流程平台负载和审批人无效工作量。

**Q5：多数据源怎么实现的？**
Druid + 自定义注解/切面（DataSourceAspect）+ ThreadLocal 上下文（DataSourceContextHolder）动态路由，底层是 Spring 的 AbstractRoutingDataSource 思路；master 主库、slave 读库、etl 数据仓库、jq（教务）外部库，跨库数据通过 ETL 数据源做同步查询。

**Q6：Redis 缓存一致性怎么保证？**
写少读多的字典型数据（房源层级），采用"更新数据库后主动失效/重写对应 Hash Key"策略（如房间变更时 `RedisUtils.hdel`），容忍极短暂不一致；用户会话走 Shiro 的 Redis 缓存。

**Q7：Excel 批量导入怎么处理脏数据？**
POI 解析后逐行校验（必填、格式、业务规则如工号是否存在），返回成功/失败明细。可补充改进点：当时是同步导入，数据量大时应改异步 + 进度查询（这是后来在公文项目里用异步队列的经验来源之一）。

**Q8：Quartz 任务怎么防止集群环境重复执行？**
单实例部署场景下用 @DisallowConcurrentExecution 防同任务并发；若集群部署，Quartz 本身支持基于数据库行锁的集群模式（qrtz_ 表），任务只会被一个节点抢到。如实说明当时部署形态即可。

**Q9：这个项目和你的公文交换平台项目有什么技术演进关系？**
本项目是 Spring Boot 单体 + Shiro + MyBatis-Plus 2.x 的经典架构，让我吃透了完整业务域建模和流程平台集成；公文项目升级到 Spring Cloud 微服务 + Spring Security OAuth2 + 多租户，两个项目正好覆盖了单体到微服务的演进路径，我能对比讲清楚两种架构的取舍（团队规模、部署复杂度、事务边界）。
